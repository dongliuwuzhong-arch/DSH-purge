# 00 · 总览与定位

> 破甲自 dsh-purge 1.1.71 分出后独立维护：宿主定版在 0.2.2-rc.5，补丁表、判据与文档只服务这一棵树，不再跟随任何外部发行节奏。

这一篇只回答一个问题的前置：**我手上这台机器，破甲到底在动什么、真源在哪、红了先看哪。**

要敲命令的细节在 02，换包在 04。这一篇读完应该能画出下面那张流程图。

---

## 一、它做四件事

| 干的事 | 落在哪 | 判据 |
| --- | --- | --- |
| **补宿主代码**：改 `resources/app` 里 `@deepseek-ai` 下的 JS / YAML | 宿主解包树（不是 asar） | 目标文件里 `grep -c "dsh-purge"` 非 0 |
| **换提示词**：把默认注入正文换成自己的，挂进系统提示 | `<DSH_HOME>/prompt-inject.md` + 三处 preset 的 `agent-instructions` | 新会话里人格只出现 1 份 |
| **桌面壳 / 换包**：把 `app.asar` 挪开让宿主回落到解包目录 | `<安装目录>/resources/` | 树检查第一条说「读的是解包目录」 |
| **shim**：PATH 上放 `dsh.cmd` / `dsh.ps1` / `dsh` | shim 目录 | `--status` 末尾三行不是 `missing` |

**为什么必须解包**：宿主默认从 `resources/app.asar` 读代码，那是只读档案。破甲把它改名成 `app.asar.bak`，宿主回落到 `resources/app` 目录，补丁才有落点。

看到什么算对：这四件事里，只有第一、二件坏了会让「补丁/人格」失效；第三件坏了会让第一件的改动**全部空转**（文件改了，宿主没在读）。第四件坏了只是命令短名不可用。

## 二、三个数据面：谁管谁

**三份东西各自独立，改一份不会同步到另一份。** 这是全篇最该先记的一张表。

| 数据面 | 文件 | 谁写 | 换宿主包会怎样 | 判据 |
| --- | --- | --- | --- | --- |
| ① 补丁表 | `lib/patches.js` + 运行副本里同一份 | 人（改仓库） | 表不变，但**锚点会被新宿主打穿** | `assert-patches` / 预检 / `--status` |
| ② profile 配置 | `<DSH_HOME>/profiles/<profile>/cordis.patch.yml` | 人（手改 YAML） | 不被覆盖，但**宿主新增的插件行不会自动进来** | 面板 / `tool_gate({action:"status"})` / `count-injections.mjs` |
| ③ 宿主文件树 | `<安装目录>/resources/app/dsh/node_modules/@deepseek-ai` | 破甲（应用时） | **整个换掉**，所有补丁回到出厂态 | 树检查 / `--status` / `grep "dsh-purge"` |

三者打架时的读取顺序：

1. **宿主树是唯一事实。** 表说「应该改成什么」，profile 说「运行时装配什么」，只有文件里的 `[dsh-purge]` 痕迹证明「确实改了」。
2. **profile 能一票否决补丁表。** 覆盖块里的 `config` 是整体替换，补丁改过的出厂 preset 在运行时可能根本不参与。
3. **补丁表只在自己的判据里有效。** `patchStatus()` 读的是宿主文件文本，不是内存里的表。

任何「补丁没生效」的怀疑，按 ③ → ② → ① 查，别从改表开始。

```bash
# ③ 宿主树里到底有没有痕迹（换一个真实目标文件）
grep -c "dsh-purge" "%INSTALL_DIR%/resources/app/dsh/node_modules/@deepseek-ai/dsh-agent-loop/lib/index.js"
# ② 运行时装配的是哪一档（覆盖块里有没有掉插件）
grep -n "tool-executor-ptc|tool-office" "%USERPROFILE%/.dsh/profiles/desktop/cordis.patch.yml"
# ① 表里的锚点今天还对不对得上
node scripts/preflight-upgrade.mjs --host "%INSTALL_DIR%/resources/app"
```

看到什么算对：③ 输出非 0；② 能定位到那两行（ptc 档要有 `tool-executor-ptc`）；① 退出码 0、末行「相对基线无漂移」。

## 四、一次「应用」会发生什么（按代码顺序）

```
对每个宿主 aiBase（通常 1~2 个）：
  1. backupAll(aiBase)           建 .dshpurge.bak（有拒建规则，见 03）
  2. restoreHookDenyForBases     仅当 settings.hooksDenyBypass === false
  3. applyPatches(aiBase)        按表顺序逐条替换（不排序 → 天然幂等）
  4. silenceCmdFlash(aiBase)     shim 那一层
  5. 记录宿主里到底有没有破甲痕迹
再在插件层：写 prompt-inject.md、装 shim、必要时解包/换包重启
```

两个后果必须记住：

- **备份永远在补丁之前**，所以 `.dshpurge.bak` 是原件。
- **补丁按表顺序贴**，所以二段补丁（锚点由前一条插入）能成立，预检也按同一顺序干跑。

## 五、四道门

四道门是四条命令，跑完各自给一个退出码。它们挡的分别是：表自洽、人格层没被动、版本对得上、文档没写错。

| 门 | 命令（仓库根跑） | 查什么 | 通过的样子 |
| --- | --- | --- | --- |
| 表 | `node scripts/assert-patches.mjs` | 条数 / id 唯一 / 每条有 name 和 file / 与 CHANGELOG 那句「补丁表 N 条」一致 | `patches=77 unique_ids=ok changelog=77`，末行 `✓ 补丁表自检通过` |
| 魂 | `node scripts/assert-soul-guard.mjs` | 注入正文 sha256 + 14 条关键补丁语义指纹 | `soul-guard ok：1 个注入文件 + 14 条破甲补丁与基线一致`，`digest a889ae52cd2e` |
| 版本 | `node scripts/assert-versions.mjs` | `package.json` 的 version / dsh.version / `release-notes.md` 首行 / `CHANGELOG.md` 首条 | `✓ 四处一致：1.5.0` |
| 文档 | `node scripts/assert-docs.mjs` | 六类：版本、宿主基线、补丁条数、用例数、行号引用、禁用词 | 六类全绿，末行「六类全绿」 |

为什么要这四道：前三条各管一份真源（表 / 人格 / 版本），第四条管的是「文档里写的数字还对不对」。

**第四条的门槛要知道**：它会跑一遍全量测试（当前 306 例）来数用例数，慢十几秒；而且只要文档里出现过期的数字就红。它红的时候先看红在哪个文件，别急着怀疑测试。

三道门的期望是「永远绿」。红了就是真事：表被改坏、人格层被动过、版本号没对齐。

第四道门的期望是「改完就绿」。它红在别人负责的文件里时，不是你的活，但要在记录里写清「红在哪、谁负责」。

## 七、为什么不跟外部发行节奏

**宿主定版在 0.2.2-rc.5。** 这不是「先跟到这个版本」，是「就到这儿」。

单值来源只有一处，文档里凡是写宿主版本的地方都指它：

| 位置 | 值 |
| --- | --- |
| `package.json` → `dshTarget` | `0.2.2-rc.5` |

- `package.json` 的 `dshTarget` 写 `0.2.2-rc.5`；预检的「破甲基准」直接读这个字段，两处必须一致。
- 补丁表、判据、文档三样只服务这一棵树。锚点按 rc.5 的出厂原文重锚过一次（1.5 那次），此后不再为别的版本维护第二套锚点。
- 三个词别混：**宿主**（DeepSeek Harness 本体）、**源码来源**（dsh-purge 1.1.71，只管出处与版权）、**宿主出厂原文**（宿主自带的那段代码/文案）。

**解冻条件**（出现哪几种情况才会再动宿主版本）：

1. rc.5 的安装包在这台机器上装不回来了；
2. 某条补丁的锚点在 rc.5 上被证明不可修（只能靠换宿主代码解决）；
3. 出现有安全性质的问题，必须换宿主版本才能解决。

三条都不满足时，任何「要不要升一下」的念头都先放下——升一次的成本是整套重锚加一次换包，不是点一下。
