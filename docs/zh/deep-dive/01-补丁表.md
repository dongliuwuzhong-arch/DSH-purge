## 一、77 这个数只有一个来源

真值在 `lib/patches.js` 的尾行：`ALL_PATCHES = [...PATCHES, ...CODE_PATCHES, ...ENGINE_PATCHES, ...NEW_TOOL_PATCHES]`。

| 段 | 数组 | 条数（实测） | 放什么 |
| --- | --- | --- | --- |
| 1 | `PATCHES` | 9 | 最早期那批：提示词、身份句、底座 |
| 2 | `CODE_PATCHES` | 3 | 沙箱 deny / 默认模式 / 审批策略 |
| 3 | `ENGINE_PATCHES` | 8 | 引擎层：审批门、升级阶梯、fs 围栏、重复调用守卫 |
| 4 | `NEW_TOOL_PATCHES` | 57 | 后加的：工具描述、desktop 壳、pi-ai、guard |

9 + 3 + 8 + 57 = **77**。

两个容易踩的事实：

1. **表不是按 id 升序排的。** 新补丁插入时按语义分段，不重排，所以 `ALL_PATCHES` 里会出现 `73 → 71 → 5` 这种跳法。**任何"按 id 顺序取一条"的写法都是错的**，要按 id 查就用 `ALL_PATCHES.find(p => p.id === N)`。
2. **唯一性靠门守，不靠人眼。** `assert-patches` 有一条 `unique_ids`——重复 id 会红。

判据命令与期望形态：

```bash
node -e "import('./lib/patches.js').then(m => console.log(m.ALL_PATCHES.length))"
# 看到 77

node scripts/assert-patches.mjs
# 看到三样：patches=77 unique_ids=ok changelog=77 / markersWritten=5 条补丁 6 个标记 声明自洽=ok / ✓ 补丁表自检通过
```

`assert-patches` 里的 `changelog=77` 是把 `CHANGELOG.md` 首节那句「补丁表 77 条」抓出来比的——**所以那句声明不是文案，是判据本身**。改表不改那句，这道门立刻红。

## 三、一条补丁长什么样

必填四件：`id` / `name` / `desc` / `file`。`desc` 的规矩是**中英各一句、中间一个 `/`**——面板和 CLI 共用它。

两种改法并存：

| 形态 | 写法 | 现网条数 | 用在什么场合 |
| --- | --- | --- | --- |
| 现代 | `replacements: [{ pattern, replace }]` + `markers` | 70 | 一个补丁改多处、要分别声明 once / 幂等 |
| 早期 | `patterns` + `replace` + `marker` | 7 | 单锚单替换：#5 #6 #7 #8 #10 #15 #16 |

早期形态能用，但**新增一律写现代形态**：早期形态没法给单个 replacement 挂 `once`，也写不出"这一处是幂等 append"。

其余字段，按"判据用途"排：

| 字段 | 作用 | 什么时候必须写 |
| --- | --- | --- |
| `file` / `rel` | 目标键 + 相对路径；键在 `targetFiles()` 里解析成绝对路径 | 永远 |
| `surfaces` | 这条只在哪些宿主面上跑（`web` / `desktop`） | 只在桌面壳或只在一面成立时。不声明 = 两面都跑（现网 73 条不声明，4 条声明 `desktop`） |
| `optional` | 目标不存在时判 `na` 而不是 `missing_file` | 目标由第三方插件/用户预设提供时（现网 36 条） |
| `markers` / `markersAny` | 认得的全部证据；`markersAny` = 任一命中即算贴过 | 永远（`markersAny` 现网 22 条） |
| `markersWritten` | 本表**真会写出**的那几条，是 `markers` 的子集 | 只要 `markers` 里混进了旧编号 / 手工标记 / 出厂原句，就必须写它，否则落地率永远失真 |
| `satisfiedBy` | 目标文件里已经写着这件事（出厂已达标），命中即"没事可做" | 宿主出厂就是目标态时（现网 1 条：#24） |
| `skipIfMarked` | 标记在就不再重贴 | 补丁是"一次性改写"，重贴会叠层时（现网 31 条） |
| `strictFiles` | 原文对不上判 `unmatched`（硬失败）而非 `skipped` | 只在"这一处必须逐字匹配、否则宁可不贴"时（现网 3 条） |
| `softSettle` | 布局类软补丁：没有残留 pattern 就算完成，不要求 marker | 目标只有装饰性标识行时（现网 3 条） |
| `once`（replacement 级） | 幂等 append：replace 里自带 pattern，打完不再叠 | insert 型补丁一律写。**现网只有 6 条补丁的自含式替换**——这是全表最该补的一处 |

```bash
node -e "import('./lib/patches.js').then(m => { const a = m.ALL_PATCHES; console.log('early', a.filter(p => !Array.isArray(p.replacements)).map(p => p.id).join(' ')); console.log('optional', a.filter(p => p.optional).length, 'markersAny', a.filter(p => p.markersAny).length, 'satisfiedBy', a.filter(p => p.satisfiedBy).length) })"
# 看到 early 5 6 7 8 10 15 16 / optional 36 markersAny 22 satisfiedBy 1
```

## 四、锚点分类（改锚时按类下手，别一条一条想）

这张表几乎全是**文本替换**，没有一条锚在结构上。锚的稳定度只由一件事决定：**命中它需要多少字节完全一致**。

按"改法"分四类：

### 甲类 · 整段代码抄写

锚是一段带缩进的宿主原文，几行到五十几行。1.5 前实测最长的一条（#69）要 2415 字符 / 56 行完全一致才算命中。

- 断的方式：宿主重排缩进、改一个变量名、加一行注释，命中率从 1 掉到 0，而**没有任何东西会报错**。
- 改法：不抄整段，改成"在稳定落点插入一个自包含块"——落点用一行 30~60 字符的唯一语句，插入块自己带 `[dsh-purge]` 前缀，重复应用靠 `once`。
- 代价：补丁从"改宿主那行"变成"在旁边加一层"，行为必须等价或更强。

### 乙类 · 长英文整段（提示词）

锚是几十到两千字符的英文正文。这类锚**永远不该逐字匹配正文**。

- 改法：锚结构键（`personaPrefix:` / `- id: tool-web` / `instructions:`），正文由一次"渲染后覆盖"完成；或者只锚该段首尾各 20 字符做区间切除。
- 判断规则：**只要一条锚里出现整句英文，就算乙类**，不管多少字符。

### 丙类 · 正则锚

主表里只有 3 条（#3 / #21 / #73）。#40 也算这一类，但它已经冷存进 `lib/patches-legacy.js`、不参与判定（见第七节）——所以「丙类 4 条」是存档区时代的口径，现在是 3。这类锚依赖"我们自己过去留下的标记"，一旦那条标记被吃掉，正则永久 0 命中，且**没有 marker 能证明它跑过**。

- #21 是全表唯一一条"无 marker"的补丁：它靠"标记不在"判已完成。这判得对，但分不清"我已还原"和"那个 raise 补丁根本没跑过"。
- #78（文件丢了从 `.bak` 拷回）是这类风险的唯一对冲。

### 丁类 · optional 且无兜底

`optional` 的补丁在目标不存在时静默判 `na`，面板只显示 `·`。**"贴不上"和"本来就不该贴"在输出里长得一模一样。**

- 判断规则：一条 `optional` 的补丁，要么有 `markers`（写下痕迹），要么有 `satisfiedBy`（出厂已达标）。两者都没有的，按配置错误处理。
- 这不是洁癖：`na` 混在分母里，会让"面板全绿"和"补丁真的生效"脱钩。

```bash
# 数一数还有多少条锚在含制表符的整段上（缩进敏感）
node -e "import('./lib/patches.js').then(m => { const n = m.ALL_PATCHES.filter(p => JSON.stringify(p.replacements ?? p.patterns ?? []).includes('\\t')).length; console.log('tab-anchors', n) })"
# 看到 tab-anchors N —— 这个数不是好坏判据，是"宿主重装后要重测的条数"
```

### 一条结构性提议（1.6 再谈）

把"多形态并列"从 `patterns` 列表里挪出来，变成每条补丁一个 `form: "rc3" | "rc5"` 字段，预检按宿主版本只跑对应形态。收益：锚点数量砍半、`na` 不再污染分母。代价：表要大改一次，所有单条测试都要跟着动。

**1.5 不做。** 宿主已经定版，多形态并列只是历史负担，不是当前风险。

## 五、两本账：`markers` 与 `markersWritten`

一句话判据：**判"贴没贴"用 `markers`，判"我们写过没有"用 `markersWritten`。**

- `markers` 是**认得的全部证据**，里面混着四类本表写不出的东西：旧编号别名（#100 的 `[dsh-purge-86]`）、2026-11-01 手打进宿主的标记（#102 的 `[dsh-fix 2026-11-01]`）、出厂原句（#24 的 `fetch: true`）、只对旧宿主有效的分支文案（#62 的 `0.2.2 tool ask failopen`）。
- `patchWrittenMarkers(p)` = `markersWritten ∩ markers`（没写 `markersWritten` 就退 `markers`）。**落地率只认它。**
- `patchApplied()` 仍然用 `markers`，并先用 `markerLooksUpstream()` 把"看着像出厂原句、且确实出现在自己 replace 里"的标记剔掉。这条剔除是 1.4.2 修的假绿：`markersAny` 混进一条出厂原句之后 OR 恒真，原件也判 applied。
- `assert-patches` 有一条自检：`markersWritten` 里的每一条必须**逐字出现在自己这条补丁的 replace 里**，且是 `markers` 的子集。

现网真值：**5 条补丁 / 6 个标记**（#24 #62 #100 #101 #102）。这五条各有各的历史账：

| id | 事 | 现在的状态 |
| --- | --- | --- |
| #24 | `markers` 里混着出厂原句 `fetch: true` | 1.5 已改成锚 id 的 `satisfiedBy`，不再靠单点函数兜 |
| #62 | 第三条标记是一句永远不出现的死标记 | 1.5 已删标记、保留 replacement |
| #100 | 挂着改号前的历史 tag `[dsh-purge-86]` | 保留（认旧标记是为了不在旧块上叠第二层） |
| #101 | replace 里写死 `[dsh-purge-89]`，与 id 错位 | 1.5 已归位成 `[dsh-purge-101]`，`markers` 同步 |
| #102 | 挂着不属于本插件命名空间的 `[dsh-fix 2026-11-01]` | 保留（它是宿主里真有的痕迹） |

**读落地率的规矩**：多目标补丁的落地率必须回到**文件级**才有意义。现网 #24 的补丁级读数是 `landedMarkers 4 / declaredMarkers 4`（四个目标各落 1 条）。历史上出现过 1/4：那时终态依然是 applied，只有落地率能看出来——而且面板不会替你区分「只落了一个目标」和「四个都落了」，两种情况的补丁级终态一样。

1.5 的结论是**先不合并**——宿主刚定版，现在动表等于把"已知可用"换成"未验证"。这张表留给 1.6。

## 八、加一条新补丁：七步

每一步都跟一条判据，做不到就别往下走。

**① 定 id。** 取当前最大 id + 1（`node -e "import('./lib/patches.js').then(m=>console.log(Math.max(...m.ALL_PATCHES.map(p=>p.id))))"` → 现在 105）。**不要复用已删 id**——存档区那 7 个号永久占着。

**② 定形态。** 新补丁一律 `replacements`。多处改动写成多条 replacement，每条单独挂 `once`。

**③ 定锚。** 先按第四节判类：能写一行唯一串就别抄整段；锚是整句英文就锚结构键；锚不唯一就先找落点。

**④ 写 `markers`，然后问一句"这句我一定写得出来吗"。** 写得出来的进 `markersWritten`；写不出来但文件里可能已有的（旧编号、出厂原句、手工标记）只进 `markers`。

**⑤ 定 `optional` / `surfaces`。** 目标由第三方插件或用户预设提供 → `optional: true`；只在桌面壳成立 → `surfaces: ["desktop"]`。

**⑥ 跑三道。**
```bash
node scripts/assert-patches.mjs        # 看到 patches=77 变成新数、unique_ids=ok、changelog 也对上
node --test test/*.test.mjs            # 看到 fail 0
node scripts/preflight-upgrade.mjs --host "<宿主树>"
# 新补丁在候选树上必须是 applied 或 na；出现 pending 说明锚没落地
```

**⑦ 改声明。** `CHANGELOG.md` 首节那句「补丁表 N 条」要跟着变，否则 `assert-patches` 红。**那句声明是判据，不是文案。**

## 附 · #19 为什么被排除

`exclude-patches.json` 里排除 `19` 不是懒，是有三条理由，2026-11-15 补记：

1. **剪枝会重写会话历史里的旧消息**（中间段换成 `[... tool result middle pruned ...]`）。前缀一变，这条消息之后的请求全部掉出 prefix cache，省下的字符未必抵得过缓存失效。
2. 被剪掉的内容模型拿不回来，需要时只能重新读文件、重跑命令，等于多花一轮。
3. 真被剪的比例很低：宿主默认阈值 8192 字符，实测工具结果平均每次一两千字符。

想要「温和档」：**排除 #19 + 把预设里 `tool-result-pruner` 的 `thresholdChars` 调到 32768**（配置层，宿主文件一个字节都不用碰）。

不要走"从 `.dshpurge.bak` 还原 + 手改预设"那条路：下一次 apply 会把 #19 重新贴回去（apply 走 replacement，不读 marker 回填），而还原错一个文件就丢掉别的补丁。

排除的生效点有六处，见 [02-判据与状态机](02-判据与状态机.md) 第六节。
