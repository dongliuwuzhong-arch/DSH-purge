# deep-dive 03 · 工程与发版

> 破甲自 dsh-purge 1.1.71 分出后独立维护：宿主定版在 0.2.2-rc.5，补丁表、判据与文档只服务这一棵树，不再跟随任何外部发行节奏。（出处：YuJunZhiXue/dsh-purge 1.1.71，MIT）

读者：改完代码要交、要发一版的人。

这一册只回答三件事：门在哪里、CI 怎么跑、包里装了什么。日常用哪条命令看 [handbook](../handbook/README.md)；判据为什么这么算看 [02-判据与状态机](02-判据与状态机.md)。

## 一、四道门，外加两道前置

「门」的定义：**它会红，而且红了必须改文或改代码**，不是打印一行看着像绿的东西。

| # | 门 | 命令 | 看到什么算对 | 它挡的是什么 |
| --- | --- | --- | --- | --- |
| 1 | 补丁表自检 | `node scripts/assert-patches.mjs` | 末行 `✓ 补丁表自检通过`，退出码 0 | 表数与 `CHANGELOG.md` 声明不一致、id 重复、`markersWritten` 与 replace 对不上 |
| 2 | 灵魂层 | `node scripts/assert-soul-guard.mjs` | `soul-guard ok`，且 digest 是 `a889ae52cd2e`（现网 lock 值） | 注入正文或 14 条关键补丁被顺手改过 |
| 3 | 版本单源 | `node scripts/assert-versions.mjs` | `✓ 四处一致：<版本>` | `package.json` version / `dsh.version` / `release-notes.md` 首行 / `CHANGELOG.md` 首条，四处不同数 |
| 4 | 文档断言 | `node scripts/assert-docs.mjs` | 六类都 `✓` + 第 7 类三条冒烟真跑过 → **末行** `七类全绿。`；有跳过时末行写「六类全绿；第 7 类命令冒烟跳过 N 条（未核）」（跳过不是通过），倒数第二行是跑到哪几条 | 文档里的版本、宿主基线、补丁条数、用例数、行号引用、禁用词；第 7 类还会真跑三条只读命令 |

两道前置（CI 里也在跑，但不算「门」——它们不检查文档或声明的一致性）：

| 前置 | 命令 | 看到什么算对 |
| --- | --- | --- |
| 语法 | `for f in lib/*.js lib/*.mjs bin/*.js bin/*.mjs scripts/*.mjs client.js; do node --check "$f"; done` | 一条都不报。CI 分两段打的是 `语法检查 42 个文件` + `脚本语法检查 9 个`（lib+bin 41、client.js 1、scripts 9；本机实测 51 个文件）；**仓库里没有 `checked=` 这种字段**，别拿它当判据 |
| 用例 | `node --test test/*.test.mjs` | `tests 356 / pass 356 / fail 0` |

**用例那条命令不能加引号。** 加引号后 shell 不展开，只剩 Node 自己的 glob——那是较新版本才有的行为，换镜像就红。也别写成 `node --test test/`：某些版本会把目录当测试文件，直接 `Cannot find module`。

### 四道门抓不到的东西（知道边界，才不会把绿当成对）

- **禁用词表原来只扫顶层，现在已经递归。** 扫描集覆盖 `root 5 / zh 2 / handbook 9 / deep-dive 5 / history 14`；往 `handbook/02` 塞一句不带否定的姿态句，第 6 类当场红（实测 2 处不符）。剩下两条边界写清楚：`history/` 按它自己 README 的声明豁免数字与行号两类（**仍计入覆盖数**，不是没扫）；soft 词只在带来源 / 出处 / 版权的行里放行。
- **文档断言只核「补丁表 N 条 / N 例」这类能机读的数。** 描述性的话写错了它不会红。
- **灵魂层门只核「注入正文 + 14 条关键补丁」。** 其余 63 条被改了它不报——那是补丁表自检和用例的事。

## 二、测试分层

`test/*.test.mjs`，实测 **53 个文件 / 356 例**。分三层，规矩是「锁语义的写在第一层，锁事故的写在第二层，剩下的随便」。

| 层 | 锁什么 | 典型文件 | 改它意味着什么 |
| --- | --- | --- | --- |
| A 判据 | 行为语义：判据函数的全部分支 | `judge` / `i3-outcome-narrow` / `d1-marker-truth` / `cycle` / `sealed-heal` / `exclude-patches` | 改了必须同时改判据、并在提交说明里写清收紧还是放宽 |
| B 回归点 | 一次具体事故 / 审计编号 | `shim-bak`（备份必须是改前原文）/ `s1-bak-guard`（0 字节 bak 不许回滚）/ `backupgap-noop` / `official-update` | 删掉等于放弃那次的教训 |
| C 边缘 | 平台细节、CLI 护栏、工具函数 | `desktop-probe`（探针 TTL）/ `surface` / `write`（rename 退避）/ `install-offline` | 可以改，但要知道它护的是哪台机器 |

两条口径事实：

1. **表驱动会多出用例。** 静态 `test(` 之外还有 `for (...) test(...)` 的写法，所以文件数 × 眼数的估算永远对不上——用例数只认跑出来的 `ℹ tests N`。
2. **有一条用例曾经依赖当前工作目录。** `install-offline` 的端到端用例在两个不同 `cwd` 下断言同一件事，CI 在 ubuntu 上探测不到安装会提前返回，于是恒绿、本机红。1.5 修的是产品侧：探测起点不再把 `process.cwd()` 排在最前。**这类「环境耦合」的用例不要靠改断言修。**

## 三、CI：checkout + 12 段

`.github/workflows/release.yml`。1.5 前是 11 段；1.5 加了「Docs assertions」，并把 Node 版本打印拆成独立一段。

| 序 | 段名 | 作用 | 顺序理由 |
| --- | --- | --- | --- |
| — | checkout | `fetch-depth: 0` + `fetch-tags: true` | 不拉全历史与 tag，后面 `git rev-parse` 永远为假 |
| 1 | Setup Node | 钉 Node 22 | 纯工具链 |
| 2 | Node toolchain | 打印 node/npm 版本进 Summary | 换镜像红的时候只看这一行 |
| 3 | Syntax-check plugin entry | 全量 `node --check`（lib / bin / scripts / client.js）+ `import lib/index.js` + `assert-patches` + `assert-versions` | 语法与表自检必须最早：后面的步骤都假设代码能加载 |
| 4 | Unit tests | `node --test test/*.test.mjs`，失败贴 `gate.log` 尾 40 行进 Summary | 用例在文档断言之前：代码不对就不必谈文档 |
| 5 | Soul guard | `assert-soul-guard` | 与用例并列的门 |
| 6 | Docs assertions | `assert-docs` | 放在门之后：文档写错不该掩盖代码红 |
| 7 | Publish / resolve version | 读 version、比对 `release-notes.md` 首行 | 发版第一步 |
| 8 | Publish / build zip | 有 tag 用 tag，否则 HEAD；`git archive` 打 zip | 必须在断言 zip 内容之前 |
| 9 | Publish / assert zip content | 拦本机基线、查必需文件、条目数下限 | 在 create release 之前，红了不产生半成品 |
| 10 | Publish / create or update release | 存在则 `gh release edit` | 正文取自 `release-notes.md` |
| 11 | Publish / upload asset | `gh release upload --clobber` | 见下面的「重发」风险 |
| 12 | Publish / verify asset | 资产数 ≥ 1 且含本次 zip 名 | 只核名字，不核字节 |

`grep -c '^      - name:' .github/workflows/release.yml` → 看到 **12**。

### 三个已知薄弱点（不是缺陷，是取舍）

1. **资产只核名字不核字节。** 同版本重发时 `--clobber` 会静默覆盖同名资产，`verify` 只看名字对得上。→ 想彻底堵，得在 upload 前比对已有资产的 sha256，不同就失败并提示升版本。
2. **每次 push main 都会触发一次发布。** 只改文档的提交也会走一遍 upload；真发新版本前先确认版本号已经提上去。
3. **注释里的数字会漂。** 有一段注释写「Node 收到的是 35 个具体文件」，实测现在是 46。**注释里不写数字**（或由脚本算）是这条的解法，不是改注释。

## 四、发版链：version → zip → release → 资产

| 环节 | 谁提供 | 现在靠什么守 |
| --- | --- | --- |
| 版本号唯一来源 | `package.json` 的 `version` | CI 第 7 段读它，写进 `GITHUB_OUTPUT` |
| 版本号一致性 | 四处：`version` / `dsh.version` / `release-notes.md` 首行 / `CHANGELOG.md` 首条 | `scripts/assert-versions.mjs`（CI 第 3 段） |
| 宿主基线 | `package.json` 的 `dshTarget` | `assert-docs` 第 2 类 + 预检读同一个字段 |
| 补丁表条数 | `lib/patches.js` 的 `ALL_PATCHES` | `assert-patches` 对 `CHANGELOG.md` 首节那句声明 |
| zip 内容 | `git archive` | CI 第 9 段的黑名单 + 必需文件 + 条目数下限 |
| release 正文 | `--notes-file release-notes.md` | 第 7 段核首行 |
| 资产落地 | `gh release upload` | 第 12 段核名字 |

发一版的顺序（照这个顺序做，任何一步红了就停在原地）：

```bash
# 1. 改版本：四处一起改（或者先只改 package.json，让 assert-versions 告诉你另外三处）
node scripts/assert-versions.mjs
# 看到 ✓ 四处一致：<新版本>

# 2. 改声明：CHANGELOG.md 首节的「补丁表 N 条」与用例数
node scripts/assert-patches.mjs && node scripts/assert-docs.mjs
# 看到补丁表自检通过 + 末行七类全绿

# 3. 全量绿了再提交
node --test test/*.test.mjs
# 看到 tests 356 / pass 356 / fail 0
```

**tag 与 zip 的关系**：tag 存在就用 tag 指向的 commit 打 zip，不存在就用 HEAD。所以「先打 tag 再 push」和「push 完再补 tag」打出来的包可能不是同一个——发完版对一下 `git rev-parse v<版本>^{}` 与 HEAD。

## 五、包内容：三条通道，各管一段

同一个仓库有三种分发物，**拦法各不相同，只改一处等于没改**：

| 通道 | 谁决定内容 | 现在拦住了什么 |
| --- | --- | --- |
| npm tarball | `package.json` 的 `files` 白名单 + `.npmignore` 兜底 | `docs/notice`（`!docs/notice`）、`scripts/preflight-baseline.json`（否定式白名单）。**注意：`files` 里的目录内文件不看 `.npmignore`**，唯一生效的是那条 `!` 排除 |
| GitHub `main.tar.gz` / `main.zip` | `.gitattributes` 的 `export-ignore` | `scripts/preflight-baseline.json`、`docs/notice/**` |
| Release zip | `git archive`（不认上面两套）+ workflow 里的剥离脚本 | 只剥 `preflight-baseline.json`；`docs/notice` 由第 9 段的断言拦（出现就红，不静默剔） |

三条通道的规矩，一句话：**`export-ignore` 只管 `git archive` 那条路，`files` 只管 npm，zip 由 CI 断言兜。**

分包时的两条判断规则：

1. **本机数据不进包。** 预检基线是「这台机器健康时的贴点记录」，跟着包发出去，别人的预检差分就变成拿我的基线比他的机器。
2. **零引用的素材不进包。** `docs/notice` 是第三方截图，仓库里留着、包里不留。

## 六、提交前清单（照抄）

```bash
node --check client.js                                   # 语法
node scripts/assert-patches.mjs                          # 表自洽
node scripts/assert-soul-guard.mjs                       # 灵魂层没动
node scripts/assert-versions.mjs                         # 版本四处一致
node scripts/assert-docs.mjs                             # 文档七类
node --test test/*.test.mjs                              # 全量用例
```

六条全绿再提交。**其中任何一条为绿而放宽，都要在提交说明里写清理由**——放宽没写理由，下一次就没人知道它原来是宽的。
