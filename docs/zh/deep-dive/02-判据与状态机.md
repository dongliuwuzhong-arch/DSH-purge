# deep-dive 02 · 判据与状态机

> 破甲自 dsh-purge 1.1.71 分出后独立维护：宿主定版在 0.2.2-rc.5，补丁表、判据与文档只服务这一棵树，不再跟随任何外部发行节奏。（出处：YuJunZhiXue/dsh-purge 1.1.71，MIT）

读者：要**改判据**或**解释一个红灯**的人。

这一册只回答一件事：一个补丁最后为什么显示成那个字。要加补丁看 [01-补丁表](01-补丁表.md)；要按状态做处置看 [handbook](../handbook/README.md)。

## 一、判定是一条三段链

```
patchAppliesHere()        宿主面过滤（web / desktop）
   ↓
patchFileOutcomeDetail()  逐目标文件出一个 state
   ↓
collectPatchStatus()      一个补丁收成一条终态（六桶）+ 一份明细
```

三个出口共用这一趟：

| 出口 | 返回 | 谁在用 |
| --- | --- | --- |
| `patchStatus()` | `{ [id]: 六桶字符串 }` | 面板、`--status`、预检 |
| `patchStatusDetail()` | `{ [id]: { state, landedMarkers, declaredMarkers } }` | 落地率核对、`purge_status` 的内部值 |
| `patchStatusWithDetails()` | 两个一起给 | `gatherState`——别为了多一列把每个目标文件读两遍 |

**为什么两套口径并存**：明细里多一档 `satisfied`。字符串口径把 `satisfied` 折回 `applied`，是因为出界消费方还不认识第五档——`scripts/preflight-upgrade.mjs` 会把未知值当 `missing`，面板和 `bin/dsh-purge.js` 会把未知值渲染成 `·`。**改字符串口径等于当场把这三个消费方判错。**

## 二、单个文件：四档

判据函数 `patchFileOutcomeDetail()`，判定顺序不能反：

| 档 | 条件 | 含义 |
| --- | --- | --- |
| `applied` | 结算了，且没有残留的「非幂等」替换能改 | 这个文件上没活要干，而且痕迹/产物在场 |
| `satisfied` | `satisfiedBy` 命中，但一条我们的痕迹都没有 | 出厂原文本来就达标 |
| `pending` | 还有活要干：`satisfiedBy` 命中但还剩非幂等替换，或没结算但原文还改得动 | 点「应用」会变 |
| `skipped` | 没结算，且原文也改不动 | 灰：再点也不会变 |

### `satisfiedBy` 只降级、不升级

`satisfiedByHit()` 只回答一件事：「这个文件里已经写着这条补丁要达成的那件事。」它**不证明我们贴过**——痕迹核对走 `markersWritten` / `landedMarkers`。

所以命中之后还要过一道 `staleActionableReplacement()`：

- 同一文件里**还留着能改的非幂等替换** → 照实报 `pending`（例：还剩一处 0 缩进的 `fetch: false`）；
- 剩下的活全是幂等 append（补一行注释那种） → 认 `satisfied`。

**这条规矩是 A10 的产物。** 反例 A（该报 pending 却报绿）就是这么被抓住的。

### 结算不等于完事

`filePatchSettled()` = `patchApplied()` 成立，或者布局软补丁已无残留 pattern。

结算之后还要回头看一眼有没有留下的活，这是 1.1.98 那次「#26 假绿」的修复：`markersAny` 是「任一标记即通过」，只改了一半也会判完成——#26 把 persona 的 prefix 改了（marker 命中），agent-instructions 那一块从来没插进去，面板绿了很久。

- 声明了 `skipIfMarked` 的按设计不再重打，维持 `applied`。
- 布局软补丁（`isLayoutSoftPatch()` = 标识行类 #4/#25/#26、审批句类 #5/#11/#12、或带 `softSettle`）**不要求 marker**，只看「没活可干」。

### `patchApplied()` 的三条路

1. `markers` 命中（`markersAny` 时任一命中；先剔掉 `markerLooksUpstream()` 认出来的出厂原句）；
2. `marker` 字段命中；
3. **产物兜底**：没有 marker 声明时，看 `replace` 首行前 60 字符在不在文件里。

产物兜底与「落地 0/1」可以并列存在，所以「同一条补丁两个文件，一个 1/1 一个 0/1，面板都绿」不是声明错。

## 三、一个补丁：六桶

`collectPatchStatus()` 把逐文件结论收成一条。**优先级从上到下，命中就停**：

```
pending → applied → unmatched → skipped → na / missing_file
```

| 桶 | 怎么来的 | 面板含义 |
| --- | --- | --- |
| `pending` | 任一目标文件还有活 | 点「应用」会变 |
| `applied` | 任一目标已结算、且没有更高优先级命中 | **「这个文件上没活可干」**，不等于痕迹在场（`satisfied` 也折进这一桶） |
| `unmatched` | 原文对不上，且这条声明了 `strictFiles` | 声明「必须逐字匹配」的补丁失配 |
| `skipped` | 原文对不上，且没声明 `strictFiles` | 灰：再点也不会变 |
| `na` | `patchAppliesHere()` 为假；或所有目标都不在候选树里且这条是 `optional` | 这条在这个面 / 这棵树上不跑 |
| `missing_file` | 同上，但这条不是 `optional` | 文件该在却不在 |

三条容易问错的：

1. **`excluded` 不是第七桶。** 被排除的 id 在进判定之前就被过滤掉了，不进任何桶、也不进分母。预检另起一行单列它，只是为了让你看见「这条存在但不算」。
2. **`satisfied` 在六桶里看不见。** 它折进 `applied`；要分这两档只能读 `patchStatusDetail()`。
3. **hooks-deny 会改写结论。** `annotateHookDenyStatus()` 只动 `pending` / `skipped`，不动 `applied` / `na`，改写后的结论同时覆盖两套口径。所以同一条在 `--status` 与 `patchStatusDetail()` 里偶尔不一样——那不是漂移，是第二遍注解。

## 四、软失败表：哪些「没贴上」不算失败

判据函数 `isPatchResultSoftOk()`。它决定应用报告里一行是 `✓` 还是 `✗`。

**永远算软**（`ALWAYS_SOFT_STATUSES`）：`applied` / `already` / `missing_file` / `skipped` / `na` / `off` / `unmatched`。

**看补丁属性才算软**：

| 行的状态 | 补丁属性 | 结论 |
| --- | --- | --- |
| `pattern_not_found` | `optional: true` | 软 |
| `pattern_not_found` | 布局软补丁 | 软 |
| `pattern_not_found` | `strictFiles: true` | **硬** |
| 其它错误文本 | —— | 硬 |

**`unmatched` 为什么也在软表里**：状态侧叫 `unmatched`，报告侧叫 `pattern_not_found`，同一个事实两个词。1.5 先把 `unmatched` 也认成软失败，免得它在软失败表里缺席、被下游当成裸 `✗`。词表合并留到下一版——改字符串会打到面板与预检的消费方。

**「软」不等于「没问题」。** 软只表示「这一行不该让整次应用判失败」。它仍然可以是：目标不存在（`na`）、锚点漂了（`skipped`）、出厂已达标（`satisfied`）。这三件事的处置完全不同。

## 五、exclude：一个清单，六个生效点

文件：`<DSH_HOME>/dsh-purge/exclude-patches.json`，形如 `{ "excludePatches": [19] }`。

读它的函数：`readExcludePatches()`；过滤函数：`withoutExcluded()` / `effectivePatchIds()`。

**六个生效点，全部走 `withoutExcluded`**：

| # | 生效点 | 少这一个会怎样 |
| --- | --- | --- |
| 1 | `applyPatches`（单树应用） | 被排除的补丁照贴 |
| 2 | `applyPatchesAllHosts`（七个应用入口都走它） | 启动自愈、reapply 链、CLI 都会贴回去 |
| 3 | `patchStatus`（`collectPatchStatus`） | 面板既显示它、又显示成「待贴」 |
| 4 | `hookDenyPaths` | 被排除的目标仍进 deny 表，`hooksDenyBypass=false` 时被强写回官方形态 |
| 5 | `patchWatchedClientBundlesSync` | client bundle 仍被当成要改的文件 |
| 6 | `gatherState` | **分母**仍算全表：被排除那条同时算进 total、又算不进 ready/applied/pending——面板「总数/就绪」永远差 1 的幽灵行 |

第 6 个是 1.5 补的。前五个少一个，行为就错；第 6 个少一个，**只是数字错**——而数字错更容易被当成「没关系」。

两条容错：

- 清单写坏（不是合法 JSON、或字段不是数组）→ 按「没排除」处理（fail-open）。宁可多贴，不要因为一个坏文件让整张表停摆。
- `applyPatchesAllHosts` 默认只打 `options.aiBase` 明确传进来的那一棵；全宿主扫描必须显式 `{ allHosts: true }`。返回值里 `hostPaths` / `skippedHosts` / `scope` 逐条给出打到哪儿，日志也逐条打印。

```bash
node -e "const {readExcludePatches}=await import('./lib/core.js'); console.log([...readExcludePatches()])"
# 看到 [ 19 ]（或别的清单）。看到 [] 说明这个 DSH_HOME 没有排除清单
```

## 六、heal：自愈判定的输入三态与七个动作

入口是启动时的 `healSealedAsarOnStart()`，纯判据是 `decideHealAction(snapshot, history)`。

**输入是快照三态 + 一份台账**：

| 输入 | 含义 |
| --- | --- |
| `s.tree` | 解包目录在不在 |
| `s.asar` | `resources/app.asar` 在不在（在 = 宿主会读它，目录永远轮不到） |
| `s.bak` | `resources` 里还躺着 `.bak` 吗（下次更新会把它复原，是定时炸弹） |
| `s.treeMarked` | 解包树里有补丁痕迹吗（`countPatchMarks()` 用宽匹配 `dsh-purge`，不要求带方括号） |
| `s.renamePending` | 上次改名失败留下的标记 |
| `history.attempts` + `history.asar` | 同一份 asar 换过几次包、最后失败原因 |

**七个动作**（`HEAL_ACTIONS`），按调用方该干什么分：

| 动作 | 触发条件 | 调用方该做的 |
| --- | --- | --- |
| `broken-no-tree` | 解包目录都不在 | 无法自愈，等用户点「应用」重新解包 |
| `needs-manual-apply` | 同一份 asar 已换过 3 次都没成 | **停手**。再杀一次 Electron 不会得到不同结果 |
| `needs-asar-rename` | 上次改名失败 | 只试一次改名；成了不杀进程，不成也不杀 |
| `needs-reapply` | asar 回来了 | 重打补丁 + 换包 |
| `needs-apply-first` | 树在但没痕迹 | **不许换包**，换了等于加载一份没打补丁的目录 |
| `needs-unbury-bak` | asar 不在，但 bak 还在 `resources` | 只挪走 bak |
| `healthy` | asar 不在、树有痕迹、bak 也没了 | 什么都不做 |

三条不变式：

1. **痕迹门槛先于换包。** 顺序写死在函数里，别改：先判 `tree`，再判 `asar`，再判痕迹，再判台账。
2. **计数只认同一个身份。** asar 的 `size + mtime` 一变，说明宿主真换了新包，计数归零（否则真升级后会退化成「再也不自动换包」）。身份缺失或对不上时一律按 0——**宁可多试一次，也不要静默放弃自愈**。
3. **没有 not-applicable 这一档。** 非桌面、定不到安装目录，由调用方在进这个函数之前就短路。留一个永远不会返回的枚举值，只会让后来读代码的人以为漏了分支。

```bash
node --test test/sealed-heal.test.mjs
# 看到 fail 0。这一份测纯函数全分支：动作 + probe 全 false 不误判 + unburyBak 的时间戳/EXDEV
```

## 七、两个真实盲区（不是猜的，是测出来的）

1. **多目标补丁的「部分完成」看不出来。** 一条补丁挂在两个文件上：一个 `applied`、另一个 `skipped`，整条仍报 `applied`（另一个是 `pending` 时整条才降成 `pending`）。面板不会告诉你哪个文件没打上——**要查只能逐文件跑 `patchFileOutcomeDetail()`**。
2. **人工把文件改回原文，状态退回 `pending`，不是 `skipped`。** 点一次「应用」还能打回来。`skipped` 只在「没结算、而且原文也改不动」时出现——那时才真的打不回来。

第三条是口径陷阱，不是盲区：**面板与 `--status` 的数字天然不同。** 面板按 `@deepseek-ai` 目录统计，桌面壳那几条（#82 #83 #84 #45 #46 #91）的 `file` 键解析到 `resources/app/lib/main.js`，在 `node_modules` 之外，会被判 `na`；预检另跑一遍 `resolveShellMain()` 把它们捞回来，单列成「桌面壳」一段。**两个数都对，只是管线两段。**

## 八、改判据的纪律

判据是这台机器上唯一还靠得住的验收手段。改它之前先问三句：

1. **是收紧还是放宽？** 只许收紧。放宽必须写明「为绿而放宽」的理由，并同时加一条反向断言。
2. **出界消费方认不认？** `scripts/preflight-upgrade.mjs`、面板、`bin/dsh-purge.js` 三处对未知值的处理是判错，不是忽略。加第五档必须同时保证这三处不炸（`satisfied` 折回 `applied` 就是为此）。
3. **有没有一条测试会因为这个改动变红？** 没有就先写测试。`test/judge.test.mjs`（判据表驱动）、`test/i3-outcome-narrow.test.mjs`（两档口径收窄）、`test/d1-marker-truth.test.mjs`（痕迹必须真写出）三份是这条线的护栏。
